## Implementation

### 1. Cancel mid-turn resolves `cancelled` (all in `takka-runtime/src/acp.rs`)

- `run_prompt_turn`: a terminal `Event::Error` that arrives while
  `Session.cancel_requested` is set now breaks the loop with
  `Ok(PromptResponse::new(StopReason::Cancelled))` instead of a JSON-RPC error.
  The engine surfaces the cooperative cancel as `AgenticError::Cancelled` →
  `Event::Error`, so the flag is the discriminator; a genuine engine error with
  no pending cancel still surfaces as an error.
- Session recovery is untouched T-03 machinery (busy cleared and receiver
  parked back *before* the response hits the wire), and the new test proves the
  session takes a second prompt after a cancelled one.

### 2. Permission bridge in the turn loop (T-06 module wired in)

- New `PermissionWaiters` registry (`Arc`-shared, owned by `AcpService`,
  cloned into each turn thread):
  `Mutex<HashMap<String outbound_id, PermissionWaiter>>` where
  `PermissionWaiter { session_id, answer_tx: mpsc::SyncSender<bool> }`.
  The session id rides along because the brief also requires per-session
  denial from `session/cancel`. Outbound ids: `acp-perm-{n}` from a
  per-connection `AtomicU64` counter.
- Turn loop: `Event::ConfirmationRequest` now calls `request_permission(...)` —
  builds the frame via `acp_permission::permission_request`, sends
  `{"jsonrpc":"2.0","id":"acp-perm-N","method":"session/request_permission","params":…}`
  through the sink, parks on the waiter, then sends
  `ProtocolRequest::new(id, acp_permission::confirm_response(None, approved))`
  so the engine unblocks and the turn continues either way. A dropped waiter
  (`recv` error) counts as deny — fail-closed, no dead-lock.
- `AcpService::route_client_response(frame)` — invoked from `handle_frame` for
  frames with no `method` but an `id` (client result/error frames). Parses
  `acp::Response<acp::RequestPermissionResponse>`: `outcome` →
  `acp_permission::outcome_approves()`; an error-shaped answer denies; a frame
  answering no known waiter is dropped silently. **Client response frames are
  never replied to** (JSON-RPC contract — previously a stray result frame fell
  into the router's catch-all and would have been answered with
  `{"ignored": true}`; that leak is closed).
- `session_cancel` denies the session's pending waiters *before* forwarding
  `Request::Cancel`, so a turn parked on a gate resumes (engine gets
  `ConfirmResponse(false)` first) and then runs the cancel to its terminal.
- `deny_pending_permissions()` (the T-07 EOF seam) is now the real
  `deny_all()` — a turn parked on a gate cannot wedge the bounded join.
- `mod acp_permission;` registered in `takka-runtime/src/main.rs`; the
  `#![allow(dead_code)]` and the "unwired until T-05" note were removed from
  `acp_permission.rs` (all four functions are now used).

### 3. Test mechanism chosen: fake-engine seam (the brief's recommended option)

The T-07 seam (`serve_over_test` + `FakeEngine` + join probe) was reused and
generalized: `TestAcp::spawn_with_fake(max_sessions, fake_engine)` (the
existing `spawn_probed` now delegates to it with `fake_engine_script`, so no
T-07 test changed). Tests drive the adapter through the real framing path
(`ChanReader`/`VecSink`, deadlines all bound by the existing 10s
`POLL_TIMEOUT`), with a parameterized scripted engine:

`fn t05_fake_engine(gate, finish_on_confirm, seen: Sender<Request>) -> FakeEngine`

- First `Run`: assistant delta, then (with `gate`) a `ConfirmationRequest`,
  then parks inside the run; later `Run`s complete immediately with `Done`
  (the cancel-recovery second prompt).
- Park loop mirrors the real engine's semantics: a `ConfirmResponse` is always
  consumed by the pending confirmation and recorded into `seen`; a `Cancel`
  ends the run with the engine's cancel terminal `Error{"cancelled"}` — but
  only once no confirmation is pending. This matters: the deny frees the gate
  asynchronously, so the forwarded `Request::Cancel` can reach the engine
  queue *before* the turn thread's `ConfirmResponse`; the fake handles both
  orders deterministically (this exact race was caught by the first test run).
- All non-`Init` requests flow into `seen` for assertions on what the engine
  actually received.

No SSE-scripted-server variant was needed; the fake engine is more
deterministic and needs no extra harness.

## Self-review

- Brief checklist item by item: all five required tests present and asserting
  real wire/protocol behavior (not implementation details); unknown-session
  cancel stays silent (pre-existing test still green); hermetic (fake engines
  or the pinned `127.0.0.1:9` config; ambient config never read).
- Concurrency audit: exactly one answer per waiter (both the routing path and
  the deny paths remove the waiter under the same mutex before sending);
  `SyncSender` capacity 1 with a parked receiver can never block; lock
  ordering is registry → waiters only in `shutdown`, no reverse nesting.
- YAGNI: no `allow_always`/`reject_always` handling beyond what T-06's
  `outcome_approves` already maps; no timeout on the gate park (user may take
  minutes; cancel/teardown are the free events — per design).
- One real bug found and fixed *by the tests* during TDD: the fake engine's
  initial park loop broke on `Cancel` before consuming a deny-unblocked
  `ConfirmResponse`, exposing the queue-order race described above; the fix
  models the real engine's flag-vs-confirmation semantics.

## Concerns (minor, non-blocking)

1. **`id: null` frames**: a client frame with explicit `"id": null` counts as
   "has an id" and routes to `route_client_response`; a null id can never
   match a waiter, so it is dropped silently — reasonable, but worth noting.
2. **Permission gate has no timeout by design**: a silent client parks the
   turn indefinitely (until cancel/EOF). This matches the CLI/daemon behavior
   and the ACP flow, but a client bug could pin a session slot; revisit if a
   client-side watchdog becomes necessary (phase 2 material).
3. **The first prompt of a session after a cancel while parked**: the engine
   receives `ConfirmResponse(false)` *after* `Request::Cancel` was queued —
   the real engine consumes it via `pending_confirmation` and then hits the
   cancel flag at the next boundary, so the deny is not lost. Covered
   indirectly by the real-engine path of test 2's fake ordering; an
   integration test against the real engine with a real provider cannot be
   hermetic, so this ordering relies on engine.rs code reading (verified:
   `pending_confirmation` sender is taken on `ConfirmResponse` regardless of
   the cancel flag).
