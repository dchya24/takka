## Implementation

Pure mapping module (no I/O, no engine, no connection state), five `pub(crate)`
functions matching the brief's signatures exactly:

| Function | Purpose |
|---|---|
| `permission_options()` | D8 default pair: `allow_once`/"Allow" (`AllowOnce`) + `reject_once`/"Reject" (`RejectOnce`). `*_always` variants are only offered on the T-05 auto-approve lane, out of scope here. |
| `permission_tool_kind(action)` | `run`/`run_command`/`run_script`→`Execute`; `write`/`edit`/`apply_patch`→`Edit`; `delete`→`Delete`; `read`→`Read`; `move`→`Move`; else `Other`. |
| `permission_request(session_id, outbound_id, action, description)` | Builds `RequestPermissionRequest`: `ToolCallUpdate` with `toolCallId = outbound_id`, flattened `title = description`, `kind = permission_tool_kind(action)`, plus D8 options. |
| `outcome_approves(outcome)` | `Cancelled`→false; `Selected("allow_once"/"allow_always")`→true; other `Selected` ids (reject_*)→false. Wildcard arm is fail-closed. |
| `confirm_response(request_id, approved)` | Wraps into `takka_core::runtime::protocol::Request::ConfirmResponse`. |

Note: `RiskLevel` (brief context #3) is intentionally not referenced — risk gating
happens in takka-core safety before a `ConfirmationRequest` is emitted; the wire
mapping is action-based only, per the brief's signatures.

assert per-field.

## Deviations from plan

1. **Wildcard arm in `outcome_approves`** (`_ => false`): the brief's sketch omitted
   it, but `RequestPermissionOutcome` is `#[non_exhaustive]`, so a wildcard arm is
   required to compile from a foreign crate. Semantics chosen: unknown future outcomes
   deny (fail-closed), documented in a code comment.
2. **No edits to the file were needed**: the file already existed as an untracked
   artifact of a prior attempt on this lane. Reviewed line-by-line against the brief,
   the ACP crate 1.16.0 sources (`RequestPermissionRequest`, `PermissionOption`,
   `PermissionOptionKind`, `SelectedPermissionOutcome`, `ToolCallUpdate` + flattened
   `ToolCallUpdateFields`, `ToolKind` snake_case serde) and
   `takka_core::runtime::protocol::Request` — all signatures, mappings, doc comments
   and the 4 required tests conform; verification then proved compile + green tests +
   clean clippy.

## Concerns

- `allow_always`/`reject_always` are accepted by `outcome_approves` (protocol-level
  robustness) but never offered by `permission_options` — T-05's auto-approve lane is
  the one that must add them when the tool is on `safety.auto_approve_commands` (D8).
- "Remember the choice" persistence for `allow_always` is client-side per ACP and
  engine-side per T-05; not this module's concern.
- When the integrator registers the module, `#![allow(dead_code)]` can stay until all
  functions are called, or be dropped once T-05 wires every function.
