## Design decisions visible in the code

- **The engine is never modified** (D10). Everything the adapter needs is already on
  the takka v2 wire protocol (`Init`/`InitOk`, `Run`, `Cancel`,
  `ConfirmationRequest`/`ConfirmResponse`), so this story adds only a host.
- **`AcpConfig.config_path` is a test seam, not a feature.** Production `serve()`
  leaves it `None` so the engine reads the user's own
  `~/.config/takka/config.json`; the tests pin a temp file instead. This mirrors
  `hermetic_runtime_config` in `takka-cli` and is the reason CI never calls a real
  provider.
- **Boot wait happens before the registry insert.** A failed boot therefore leaves
  no slot behind — capacity is not leaked by a broken provider config.
- **Turn results are written after the state is restored** (receiver re-parked,
  `busy` cleared) so a client that saw the response can prompt again immediately.

## Deviations from the brief

1. The brief asked for `--acp-max-sessions` to be *documented only* (the flag was
   wired by the T-07 lane in `main.rs`, because it needed the same parse path for

2. The brief's optional subprocess smoke became `takka-runtime/tests/acp_smoke.rs`
   (written by the T-07 lane, still the only subprocess test).

## Concerns

- `session/new` holds the framing loop for up to `BOOT_TIMEOUT` (10s) while an engine
  initialises. ACP clients spawn one agent per project, so this is the intended
  shape, but a slow config (network LLM key validation) is visible to the client as
  latency, not as concurrency.
- Capacity is per-connection, not per-machine: each client process gets its own 4
  slots (D6's model — one process per project).
